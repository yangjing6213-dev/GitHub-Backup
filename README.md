## 一、这个项目是什么？

这是一个正在开发的本地备份应用，不是需要安装到 AI 助手里的 Skill，也不是提示词集合。仓库同时保留了早期的命令脚本，方便追溯和继续开发；普通用户应优先阅读本页的桌面版说明。

你提供自己的 GitHub 账号和本机保存目录，通过浏览器登录并确认备份授权。程序检查环境后，读取这个账号**自己拥有的仓库**，将代码、版本历史及支持的项目资料保存到本机。

它不是粘贴任意 GitHub 项目链接的下载器，也不负责把备份自动上传回 GitHub。

## 二、先看效果

目前没有可以公开展示的真实界面截图或完整备份案例。下面是根据代码整理的**输出结构示例**，不是本次已经完成的备份结果。

假设你用自己的账号运行一次日常备份，保存位置选择 `D:\GitHub-Backups`，程序会按账号和项目整理资料：

```text
D:\GitHub-Backups\<你的账号>\
├─ mirrors\<项目名>.git\              项目代码与版本历史
├─ wikis\<项目名>.wiki.git\            存在的 Wiki 内容
├─ metadata\<项目名>\
│  ├─ repository.json                  仓库资料
│  ├─ issues.pages.json                问题记录
│  ├─ pull-requests.pages.json          代码合并请求资料
│  └─ releases.pages.json              发布信息
├─ manifests\summary-<运行编号>.json    本次结果摘要
└─ logs\backup-<运行编号>.log           本次运行日志
```

其中，`.git` 文件夹是仓库镜像，主要用于保存版本历史，不是可以直接双击打开的普通项目工作文件夹。`JSON` 是结构化文本文件，可以用文本编辑器查看；日志用来了解哪一步成功或失败。

选择“完整备份”时，还会在 `releases\<项目名>\` 保存支持下载的发布附件。你可以按照[快速开始](#六安装与快速开始)尝试自己的账号，再通过“打开备份目录”和“查看最近日志”检查实际输出。

## 三、适合谁用？

### 特别适合

- 用 AI 搭建了多个项目，希望给自己的 GitHub 账号保留本地副本的创作者。
- 同时管理代码、问题记录、Wiki 和发布文件，希望统一整理的人。
- 希望用中文窗口检查备份状态，而不是每次手动运行多个脚本的人。

### 不适合

- 只想输入某个他人项目网址，下载这一份代码的人：当前桌面版按登录账号拥有的仓库工作。
- 需要已验证的正式安装软件、无人值守定时备份，或一键恢复到远端的人：这些不是当前已交付能力。
- 使用 macOS、Linux、Windows ARM64，或只能将资料保存到网络盘的人：当前构建目标是 Windows x64，本机固定磁盘。

不需要懂编程，但需要会下载文件、选择文件夹，并能通过浏览器完成自己的 GitHub 登录。当前测试版仍有额外工具要求，见下文。

## 四、你会得到什么？

按现有代码，备份产物包括：

- 仓库镜像和版本历史；项目使用 Git LFS 时，同时保存其大文件对象。Git LFS 是 GitHub 项目存放大文件时使用的配套工具。
- 仓库存在 Wiki 时的 Wiki 镜像。
- 仓库资料、问题、合并请求、评论、标签、里程碑、发布信息和工作流资料等 `JSON` 文件。
- 完整模式下载的发布附件，以及附件索引。
- 每次运行的仓库清单、结果摘要和日志。

默认备份根目录是 `D:\GitHub-Backups`，可以在界面选择其他合格目录。实际内容位于其下的账号文件夹；不要随意编辑镜像和索引，以免影响之后更新。

应用设置和诊断文件另存于 `%LOCALAPPDATA%\GitHubBackupTool\`，不全在备份盘。这个路径指当前 Windows 用户的本地应用资料文件夹；运行后才会产生相应资料。

## 五、它能帮你解决什么问题？

手动备份时，你通常要分别处理仓库、发布文件和结果检查。桌面版把这些操作集中到一个入口：先检查所需工具和保存目录，再选择日常或完整模式，最后查看结果。

日常模式不下载发布附件，适合重复更新；完整模式用于需要一并保存发布文件的情况。网络设置限制在本次备份的进程或临时配置内，避免备份结束后留下全局 Git 配置改动。

你仍然需要完成登录、同意必要操作、保证网络和磁盘空间，并检查备份摘要。项目没有证据支持“保证全部成功”或“节省多少时间”的承诺。

## 六、安装与快速开始

### 先准备什么

必需条件：

- Windows 64 位电脑（x64），可以访问 GitHub 的网络，以及自己的 GitHub 账号。
- 本机固定磁盘上的备份文件夹，建议使用 NTFS 磁盘。不能选择磁盘根目录、网络盘、可移动磁盘或目录链接。
- 足够保存项目和临时文件的磁盘空间；不是只预留 1 GB 就一定足够。
- Git、GitHub CLI（命令名为 `gh`）和 Git LFS。这些是程序进行备份和登录的配套工具，不是 AI 模型。

当前代码设置的工具最低版本为 Git `2.55.0.windows.3`、GitHub CLI `2.100.0`、Git LFS `3.7.1`。这是本项目的检查要求，不代表这些工具各自的官方最低要求。

程序提供“检测与安装依赖”入口。已达标的软件不必重装。只有通过程序安装缺少或旧版本工具时才需要 Windows 的软件安装工具 winget，当前代码要求 `1.29.290` 或更新版本；不具备时，可先通过 [Microsoft Store 官方页面](https://apps.microsoft.com/detail/9nblggh4nns1)安装“应用安装程序”，或按窗口内官方地址手动安装配套工具。

主程序自带 .NET 运行环境，不要求普通用户为了启动额外安装 .NET SDK。不过，干净电脑上的运行情况尚未验收。网络代理属于可选配置，没有连接问题时不必先设置。

本地代码不要求调用付费 AI 模型。GitHub 服务、网络和存储仍取决于你自己的使用条件；本页不作永久免费或商业使用授权承诺。

### 安装包下载与安全检查

请从 [GitHub Releases 发布页](https://github.com/yangjing6213-dev/GitHub-Backup/releases)查看有明确版本说明的安装包和校验值。下载页可能同时保留较早测试 ZIP；它不包含本轮安装器修复。只有当发布说明明确列出新版 `GitHubBackup-setup.exe` 及对应 SHA-256 校验值时，才把它作为本轮修复版下载；找不到该文件时，不要把旧 ZIP 当作最新版，也不要拼接下载地址。

安装包适用于 Windows 11 25H2 x64（系统版本 26200），请用普通用户身份运行，不要选择“以管理员身份运行”。它会固定安装到 `%LOCALAPPDATA%\Programs\GitHubBackupTool`，创建桌面和开始菜单图标，并在当前 Windows 用户的“已安装的应用”列表中登记卸载入口。卸载只移除经过核验的本程序文件和快捷方式，不会删除备份、设置、日志或凭据。

如果安装时提示发现旧版本，请按提示进入安装目录运行 `Uninstall.exe`，然后重新运行新安装包。不要手动删除安装目录中的文件。安装包尚未签名，Windows 可能显示“未知发布者”；请先确认文件来源，不要关闭系统保护。

### 已发布的旧测试版 ZIP（不含本轮修复）

1. 阅读当前[测试版发布说明](https://github.com/yangjing6213-dev/GitHub-Backup/releases/tag/build-preview-20261001)，然后下载 [Windows x64 测试版程序包（ZIP）](https://github.com/yangjing6213-dev/GitHub-Backup/releases/download/build-preview-20261001/GitHubBackup-win-x64-preview-20261001-02.zip) 和[校验值文件](https://github.com/yangjing6213-dev/GitHub-Backup/releases/download/build-preview-20261001/SHA256SUMS-preview-20261001-02.txt)。这是开发测试版，不是正式版。
2. 将 ZIP 解压到你新建的文件夹。里面应有 `GitHubBackup.exe` 和许可说明 `NOTICE.txt`；只有前者是程序。保留许可说明。GitHub 自动生成的 `Source code` 压缩包只是源码，不是可运行程序。
3. 双击 `GitHubBackup.exe` 后，应看到中文备份窗口。当前程序未签名，Windows 可能提示来源未验证：不要关闭安全软件或盲目忽略提示；先核对下载来源，不能确认时停止使用。

此旧 ZIP 不含本轮修复的安装程序；其中的程序仍需解压后直接运行。以上窗口操作来自现有界面与代码核对，**尚未完成真实试用验收**。

### 第一次使用的最小示例

1. 在主窗口把默认作者账号 `yangjing6213-dev` 改为**你自己的 GitHub 用户名**，不是邮箱，也不是项目网址。
2. 点击“检测与安装依赖”查看状态。**已达到最低版本的软件会显示“无需安装”；复选框只表示同意，不会自动安装。**只有确实缺少或版本过旧时，才需要勾选并点击旁边可用的“安装”按钮。程序内安装需要 winget；如果窗口说明它不可用，请先通过 [Microsoft Store 官方页面](https://apps.microsoft.com/detail/9nblggh4nns1)安装“应用安装程序”，再重新检测。之后点击“重新检查环境”。
3. 选择备份目录，例如 `D:\GitHub-Backups`；没有 D 盘时，自己选择其他本机固定磁盘里的新文件夹。点击“验证并保存目录”，需要创建或修复权限时先阅读提示。
4. 阅读原样保存和凭据使用提示。明确同意后点击“浏览器登录”，程序会尝试自动打开 GitHub 官方设备登录页；如果浏览器没有打开，请访问 `https://github.com/login/device`，并输入程序界面显示的一次性代码。完成登录后重新检查环境。该登录会使用当前 Windows 用户共享的 GitHub 凭据库，可能影响其他 `gh` 工具的当前账号。
5. 先选择“日常备份”。环境检查通过、“开始备份”可用后点击开始。**它会处理这个账号拥有的仓库，不只处理一个示例项目。**
6. 等待结果后，点击“打开备份目录”和“查看最近日志”。查看本次摘要，而不是仅根据文件夹已经存在判断成功。

如果检查不通过，先处理界面指出的项目，不要为了让按钮变为可用而随意降低安全设置。

### 源码方式（供继续开发的人）

需要 .NET 10 SDK，在项目根目录的 PowerShell 中构建。下面是项目使用的构建方式，不是普通用户的安装步骤；`artifacts\publish\preview` 应为没有旧文件的新输出目录。

```powershell
dotnet restore src/GitHubBackup.App/GitHubBackup.App.csproj --locked-mode
dotnet build src/GitHubBackup.App/GitHubBackup.App.csproj --configuration Release --runtime win-x64 --no-restore -t:Rebuild -p:DebugType=None -p:DebugSymbols=false
dotnet publish src/GitHubBackup.App/GitHubBackup.App.csproj --configuration Release --runtime win-x64 --self-contained true --no-restore --no-build -p:DebugType=None -p:DebugSymbols=false --output artifacts/publish/preview
```

当前机器已成功执行主程序重新编译和单文件发布；没有在新电脑上完整执行上述下载、还原及试用流程。详细构建说明见 [publish/README.md](publish/README.md)。普通用户不需要执行源码构建步骤。

## 七、如何使用？

日常更新：打开程序，确认账号和目录，完成环境检查，选择“日常备份”后开始。结束时检查本次结果：

- `PASS`：本次摘要报告成功，仍建议核对所需项目是否在范围内。
- `PARTIAL`：只完成一部分，查看摘要和日志了解缺失项。
- `FAIL`：本次运行未通过，处理原因后再试。
- `CANCELLED`：运行被取消，不能当作完整成功。

需要发布附件时改选“完整备份”。更改保存位置要重新验证；不要在备份过程中手动移动、删除或修改目标文件。

程序提供取消和“重试清理”入口。遇到清理未完成的提示，先按提示处理，再开始下一次；关闭窗口不代表所有步骤已经成功结束。

需要反馈故障时，可以使用“预览并导出诊断”，先检查导出内容，再自行决定是否分享。不要上传原始备份、凭据或未经检查的日志。

## 八、项目工作流程

填写自己的账号和保存目录 → 检查工具、空间和目录 → 用户确认必要操作并登录 → 选择备份模式 → 程序读取仓库与资料 → 用户查看本次摘要和日志。

登录、安装工具、创建或修复目录等涉及你的电脑或账号，由你决定是否同意；仓库读取、分类保存和结果记录由程序处理。最后一步仍需要你确认结果覆盖了实际需要保存的内容。

## 十、注意事项与常见问题

### 备份会不会修改 GitHub 项目？

桌面版备份流程读取 GitHub 内容，不负责上传恢复。但仓库中的独立旧恢复脚本可以向远端推送镜像，不是普通备份入口，使用前需要另外评估覆盖风险。

### 私有项目和敏感资料怎样处理？

程序只读取登录账号有权限访问、且由该账号拥有的仓库。原始备份不做脱敏：代码、历史提交和项目资料里已有的秘密也可能原样保存。不要将备份目录同步到公共空间。

应用经明确同意后，会读取 Windows 凭据库中指定账号的凭据，并仅在内存中用于只读请求，不另外保存、显示、记录或导出该凭据。浏览器登录本身会由 GitHub CLI 写入 Windows 共享凭据库；不能理解为“整个登录过程从不存储凭据”。

日志有脱敏处理，备份目录使用权限限制；这不等于加密，也不能保证电脑管理员无法访问。诊断导出和任何对外分享仍需要人工检查。

### 检查后仍不能开始？

可能缺少配套工具、工具版本不符合项目要求、登录账号不匹配、目录不合格或空间不足。根据窗口中的具体提示处理后重新检查；没有 D 盘时手动选择其他目录，程序不会悄悄替你改路径。

### 我勾选了依赖，但“安装”按钮仍然不能点？

勾选只表示同意下载和许可；还要点旁边的安装按钮才会开始。若检测版本已达到最低要求，窗口会说明“无需安装”，这是正常情况。若版本缺少或过旧，窗口会显示 winget 是否可用；winget 不可用时，请先按窗口提示从 Microsoft Store 安装“应用安装程序”，再重新检测。不要为了解决按钮变灰而关闭安全保护。

### 网络连接失败怎么办？

遇到超时、连接被拒绝或重置等中断时，程序会先按策略重试；适用时再尝试 Windows 系统代理。网络设置只用于本次备份，不改全局 Git 设置。它不能解决所有网络问题；账号权限、证书错误和 GitHub 限流应按提示处理或等待。

### 这些备份能替代全部 GitHub 数据吗？

不能。工作流资料不等于每次 Actions 运行的日志或构建产物；子模块不会递归抓取。当前没有已完成的桌面恢复、定时备份和任意仓库筛选功能。不要仅凭 `PASS` 推断所有 GitHub 功能的数据都有副本。
